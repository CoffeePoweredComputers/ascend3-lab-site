Turn everyone's own codes into one codebook two people would apply the same way. Wiki: [the codebook and team coding](/wiki/qualitative/codebook-and-team-coding).

## Structure

A **dimension** is one question asked of every item. Each is about either the diagram or the reflection, and the coding form groups them that way.

- **Single choice**: exactly one code applies. Include an "unclear" option.
- **Multi-label**: any number apply, including none.

Each code has a label, a definition, include when, exclude when, and an example with its item id. Most disagreements are fixed in "exclude when".

## The merge

1. The lead runs the merge, once. It groups codes that mean the same thing and proposes a name and definition for each group. Diagram codes and reflection codes are never grouped together.
2. Meet, with one screen shared. For each personal code, choose where it goes: into a proposed code, a code of its own, or dropped.
3. Rewrite names and definitions until everyone would apply them the same way.
4. When nothing is undecided, write the result to the codebook draft.

## The draft

1. Sort the codes into dimensions.
2. Write all five parts for each code, with the items open.
3. Have someone who did not write a definition apply it to two items.
4. Publish with a note. Anyone can.

Start with about eight codes.

## Starting points

- **Diagrams**: what each box is, what the lines mean (order, call, data flow), and issues. The ICER 2026 issue codes that do not depend on the assignment are worth trying: clashing notations, ambiguous order, repeated functionality, too many responsibilities, vague language, non-meaningful names.
- **Reflections**: what the student says was hard, and separately how they feel about the exercise.

## Versions

- A published version never changes. To change anything, start the next draft and publish it with a note.
- Keep a code's key the same across versions. Use a new key if its meaning changes.
