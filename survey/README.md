# Adaptive survey service

A small web service for **adaptive surveys**: a participant answers fixed "starter"
questions in a typed conversation; after each answer a language model decides whether to
ask one more follow-up probe (from a fixed protocol — DICE for the first study) or to move
on. Participants can press **Next question** to skip the rest of a starter's dialogue and
**Stop** at any time; whatever they entered is kept.

It runs beside the static ASCEND site on `ascend3.cs.vt.edu`, proxied by nginx at
`https://ascend3.cs.vt.edu/survey/`. First use: **VT IRB #26-817** (`surveys/irb-26-817.json`).

A survey is either a **file** in `surveys/` (the IRB study: reviewed, versioned, deployed
with the code) or **created on the admin page** (`/survey/admin` → New survey: title,
questions, follow-ups per question, closing date, consent text). Both kinds are the same
config, validated by the same schema and hashed to the same config version; created ones are
stored in Postgres (`survey.surveys`) instead of a file.

## What the protocol commits us to — and where each commitment lives

| Commitment | Where it is enforced |
| --- | --- |
| VT single sign-on | `src/auth/cas.ts` — `login.vt.edu` CAS; signed, path-scoped cookie |
| Study data in Postgres on VT infrastructure; every turn records probe type, trigger, config version | `migrations/001_init.sql`, `src/engine/session.ts` (`survey.turns` is append-only for the app role) |
| Model calls only to `llm-api.arc.vt.edu`; model sees only the current starter's exchanges | `src/llm/arc.ts`; `src/engine/prompt.ts` is the only place model input is built |
| Identity never joined to responses; key held apart, exportable only by the keyholder, destroyable | two schemas + two DB roles with no cross-`USAGE` (`migrations/`), `src/store/keyring.ts` vs `src/store/survey.ts`, keyholder routes in `src/routes/admin.ts` |
| Consent before any research content; info sheet always available | `src/routes/participant.ts` (no session without an enrollment), `/s/:id/info-sheet` |
| No third-party analytics/error tracking; no response text in logs | the page loads only its own files (CSP in `src/app.ts`); `src/log.ts` policy |

## Layout

```
surveys/<id>.json     file-defined surveys (validated by src/config/schema.ts at boot; hash = config version)
surveys/survey.schema.json   editor schema generated by `npm run schema` (autocomplete + field docs)
templates/minimal.json       starting point for a new study (`npm run new-survey`) AND the base for surveys created on the admin page (src/config/create.ts)
scripts/              validate, schema, new-survey, bench-model (run with `npm run <name>`)
migrations/*.sql      schema, applied once each by `npm run migrate`
src/                  TypeScript service (Hono + pg + zod)
web/                  participant page, admin page, styles — plain HTML/JS, no bundler
test/                 node:test — parser, CAS, monitor, config, and an in-process end-to-end run against Postgres
deploy/               systemd --user unit, deploy.sh (called by ../autodeploy.sh), provision.sql
```

## Local development

```bash
cd survey
npm install
docker run -d --name ascend-survey-pg -e POSTGRES_PASSWORD=postgres -p 127.0.0.1:5433:5432 postgres:16
sed -e 's/CHANGE_ME_OWNER/owner_dev/' -e 's/CHANGE_ME_SURVEY/survey_dev/' -e 's/CHANGE_ME_KEYRING/keyring_dev/' deploy/provision.sql \
  | PGPASSWORD=postgres psql -h 127.0.0.1 -p 5433 -U postgres -v ON_ERROR_STOP=1 -f -
cp .env.example .env      # then set: NODE_ENV=development, LLM_PROVIDER=mock, DEV_LOGIN_ENABLED=1,
                          # BASE_URL=http://127.0.0.1:8787/survey, the three *_DATABASE_URLs on port 5433
npm run migrate:dev
npm run dev               # http://127.0.0.1:8787/survey/
npm test                  # parser + CAS unit tests; e2e runs when the database is reachable
```

Sign in locally with `http://127.0.0.1:8787/survey/auth/dev-login?pid=<pid>` (only honoured
when `NODE_ENV != production`, `DEV_LOGIN_ENABLED=1`, and the request comes from loopback).
Use a PID listed in a survey's `roles` to see `/survey/admin`; from there **Start a preview
session** opens the instrument without consent and outside wave windows, flagged so it is
excluded from exports. `LLM_PROVIDER=mock` gives deterministic follow-ups; set
`LLM_PROVIDER=arc` and `ARC_LLM_API_KEY` to try the real model.

## Creating a survey on the admin page

For anything that does not need a reviewed file in git: open `/survey/admin`, press **New
survey**, and fill in a title, the questions (one per line), follow-ups per question (0–3, default
1), a closing date, and the consent text (a generic notice is prefilled; paste the approved sheet
for a study). Opening/closing lines and the model's follow-up instructions are under *Advanced*
and default to `templates/minimal.json`. The result is an open, single-wave survey whose
participant link (`/survey/s/<id>`) is shown on its card with a Copy button; you are its
researcher and keyholder. **Close survey** (keyholder section) stops new sessions; there is no
delete. Who may create is `SURVEY_ADMINS` in `.env`; when that is empty, anyone holding the
researcher role on a file-defined survey may.

The keyholder section of every card has the identity-key download (logged), Close, and, once
closed, Destroy key. A roster editor appears there only for surveys whose file sets
`eligibility.roster`. The key-event audit trail (`keyring.key_events`: every export, roster
replacement and destruction, with the actor PID) is no longer shown on the page; read it with
`GET /api/admin/s/<id>/key-events` or in the database.

## Reusing the instrument for a new study (as a file)

The service hosts any number of surveys; each is one JSON file. Nothing about DICE, CS 2114, or
the IRB study is hard-coded — the questions, prompt, probe taxonomy, limits, consent text, roles,
and model all live in the file.

```bash
npm run new-survey -- my-study "My Study"   # copies templates/minimal.json → surveys/my-study.json (status: draft)
npm run validate                             # same loader the server runs at boot
npm run dev                                  # admin → "Start a preview session" to try the prompt with the real model
```

Then edit the file (your editor gets autocomplete and field docs from `"$schema": "./survey.schema.json"`):

| You need | Set |
| --- | --- |
| Who may read coded results / export the identity key | `roles.researchers` / `roles.keyholders` (PIDs). Keep course staff out during a course study. |
| The fixed questions | `waves[].starters[]` — listed in full per wave, worded exactly as approved |
| When participants may start | `waves[].opensAt` / `closesAt`; one session per participant per wave |
| The consent screen | `consent.sheetMarkdown` (your approved sheet), `agreeLabel`; `consent.ferpa` only if you need a separate records release; `eligibility.roster` if only listed PIDs may enrol |
| The probing behaviour | `probing.systemPrompt` (must output `MOVE_ON` or `{"probe_type","trigger","question"}`), `probeTypes`, `maxProbesPerStarter`, `maxTurnsPerSession` |
| Speed / quality | `model.name` (see `npm run bench:model`), `maxTokens` ≥ 1200 for reasoning models |

Commit and push; the deploy validates the file again before restarting. Every distinct file
content is recorded as a **config version**, and sessions already in progress keep the version
they started with, so editing a live survey never changes what a participant is mid-way through.

Two seams are Virginia Tech-specific and would be swapped for another institution:
`src/auth/cas.ts` (CAS login → PID) and `src/llm/arc.ts` (OpenAI-compatible client for ARC).
Everything else is generic.

Roles are the only access control: `roles.researchers` may see and export **coded** data and run
previews; `roles.keyholders` may upload the roster, export the PID↔code key (each export is
logged), and destroy the key once `status` is `closed`. For a course study, keep course staff out
of both lists during the semester.

## Piloting with testers who have no VT account

Everything above assumes VT single sign-on. To try an instrument on people outside the
university, set `eligibility.guestAccess: true` on a **pilot** survey file and hand out a signed
invite link:

```bash
npm run invite -- pilot          # link valid 30 days; `-- pilot 7` for a week
```

One link serves everyone: each person who opens it is issued a fresh `guest:<random>` identity, so
their transcripts stay separate, and reopening the link resumes rather than restarting. The token
is an HMAC over the survey id (`src/auth/guest.ts`), so it is only good for that one survey and
only while its file opts in.

Guests are contained by construction rather than by a check that could be forgotten:

- `guest:<random>` cannot match a PID (`/^[a-z0-9][a-z0-9._-]*$/` admits no colon), so a guest can
  never appear in `roles` and can never hold researcher or keyholder — there is no value of the
  invite token that yields an admin session.
- Any survey whose file does not set `guestAccess` returns 404 to a guest, so an invite to the
  pilot is not a way into a live study.
- `dev-login` remains loopback-only and refused in production; the invite route does not change it.

**Leave `guestAccess` false on anything collecting research data.** It is the one switch that
bypasses VT single sign-on, and consent, roster checks, and the identity keyring all assume a real
PID behind the session. Pilot data is not research data: keep it in its own survey file and delete
it when testing ends.

## Server provisioning (one time, on ascend3.cs.vt.edu)

```bash
node --version                                   # must be >= 20
sudo apt install postgresql
sudo -u postgres psql -f ~/ascend3-lab-site/survey/deploy/provision.sql   # after editing the three passwords
cd ~/ascend3-lab-site/survey && cp .env.example .env && chmod 600 .env    # fill in secrets + DB URLs
sudo loginctl enable-linger "$USER"
mkdir -p ~/.config/systemd/user && cp deploy/ascend-survey.service ~/.config/systemd/user/
systemctl --user daemon-reload
./deploy/deploy.sh                                # npm ci → build → migrate → (re)start → health check
systemctl --user enable ascend-survey
sudo cp ~/ascend3-lab-site/nginx-configs/ascend3.conf /etc/nginx/sites-available/ && sudo nginx -t && sudo systemctl reload nginx
curl -fsS https://ascend3.cs.vt.edu/survey/healthz
```

After that, **pushing to master deploys**: `autodeploy.sh` runs `survey/deploy/deploy.sh` whenever
a pull touched `survey/`. A failed migration stops before the restart, so the old process keeps
serving. Logs: `journalctl --user -u ascend-survey -f`.

Backups: schedule `pg_dump -Fc ascend_survey` nightly (e.g. from the same crontab) to a
VT-managed location. Whether the VM disk counts as *encrypted at rest* and whether a CS-managed
VM counts as *centrally managed storage* are questions for PRDP (prdp@vt.edu), not for this code.

## Data model (short)

Schema `survey` (role `survey_app`, no `DELETE`): `survey_configs` (every version ever booted or
created), `surveys` (which version is current for each survey created on the admin page),
`participants` (by **code** only), `sessions`, `turns` (append-only transcript: `starter`,
`probe`, `answer`, `advance` with `trigger` = why the starter ended, `stop`), `llm_calls`
(exact request + raw response for every model call).

Schema `keyring` (role `keyring_app`): `enrollments` (survey, **PID**, code, FERPA name/date),
`rosters`, `key_events` (export / roster_replace / destroy audit).

Exports (researcher): `sessions.csv`, `turns.csv`, `transcripts.jsonl` — coded only; previews
excluded unless `?includePreview=1`. CSV cells starting with `= + - @` are prefixed with `'` to
stop spreadsheets executing them; the JSONL is verbatim and is the canonical analysis input.
Keyholder: `keyring.csv`.

## Viewing results

On `/survey/admin` each survey card is a grid: one row per participant session, one column per
question and one per follow-up slot (`Q1`, `Q1 follow-up`, `Q2`, …). A follow-up cell shows the
question the model asked that participant above their answer; an empty cell means that
follow-up never happened (the model moved on, errored, or the participant skipped). Pick the
wave when a survey has several; tick *include previews* to see your own test runs. Everything
here is coded: no PID can reach these routes because they run on the `survey` pool, which has
no access to the `keyring` schema.

For analysis, download `results.csv` (the same grid, one `(question, answer)` pair per
follow-up) or `transcripts.jsonl` (canonical, with probe types, triggers and why each question
ended). `turns.csv` and `sessions.csv` and the per-session JSON are still served at the same
URLs for scripts.

## Model connectivity light

The header of both pages shows the model state. The service wraps the model client so every real
call is recorded, and probes ARC once a minute with a token-free `GET /models` (which also fails
when the key is revoked). States: **connected**, **slow or failing** (last call failed or took
over 10 s), **unavailable** (probe failed or two calls in a row failed), **checking**. Participants
see a short label and, when the model is unavailable, a note that follow-ups are paused and their
answers are still saved — because that is what the engine does: it never blocks on the model.
`GET /survey/healthz` includes the same state for monitoring.

ARC is reachable only from campus. The production VM is on campus; a development laptop off
campus needs the VT VPN, otherwise every call fails with HTTP 403 and the light goes red.

## Continuous integration

`.github/workflows/survey-check.yml` runs on any change under `survey/`: typecheck, `validate`,
`schema --check`, and the full test suite against a Postgres service (so the end-to-end tests run
in CI too). It never builds the Astro site.

## Operational notes

- The model never blocks a participant: a timeout, transport error, or unparseable reply
  advances to the next starter and is recorded as `llm_error` / `parse_error`.
- An answer is committed before the model is called; if the process dies in between, the next
  page load finishes the decision.
- `DEV_LOGIN_ENABLED`, `LLM_PROVIDER=mock`, and short `SESSION_SECRET`s are refused when
  `NODE_ENV=production`.
- There is no per-user request throttle (removed 2026-09-20: it keyed on client IP, which a
  lab or campus NAT shares). The expensive path, a model call, is bounded per session by
  `maxTurnsPerSession` and serialised per session by the engine.
- ARC's documented limits (docs.arc.vt.edu, 2026-09): concurrency **10** for `gpt-oss-120b`
  (scope per key vs. global not stated), 8 000 tokens per non-streaming request, no request-rate
  or daily-token figure for chat. Over the limit, requests are "rejected"; the engine records
  `llm_error` and moves on, so participants never wait on it.
- Reminder emails are not sent by the service; the keyholder exports `keyring.csv` and mails
  from it.

## Choosing a model

`npm run bench:model -- --runs 3 gpt-oss-120b gpt-oss-120b-thinking-low DeepSeek-V4-Flash` times candidate
ARC models against the survey's real probe prompt and shows whether each reply parsed. On 2026-09-06
`gpt-oss-120b-thinking-low` averaged 1.5 s per follow-up versus 3.6 s for `gpt-oss-120b`, with the same
probe choice, so the first survey uses it. `model.reasoningEffort` (`low|medium|high`) is also sent as
`reasoning_effort` if you prefer the base model id. Reasoning models count their thinking against
`model.maxTokens`; keep it well above the JSON you expect (default 1200) or replies truncate.
