Three designs keep the order; sorting on access does not

Four class pictures side by side, one per press, with a caption under them. A, from scratch: one class, SortedList of T, with the members Node firstNode, add of T, remove of T, getPosition of T and getEntry of int, and its own chain 3, 7, 12 under it. B, inheritance: a box LList of T with add of int and T, replace of int and T, and getEntry of int; under it a box SortedList of T with add of T, and add of int and T and replace of int and T in maroon, each marked throws; a generalisation arrow with a hollow triangle runs from SortedList up to LList. C, composition: a box SortedList of T with add of T, getPosition of T and getEntry of int, joined by a line with a filled diamond, labelled list, to a box LList of T with add of int and T and getEntry of int; the caption gives add as list dot add of Math dot abs of getPosition of newEntry, newEntry, O of n on an array list and O of n squared on a linked list. D, sort on access: a box SortedList of T with add of T and getEntry of int over an unsorted row 7, 20, 3, 12. Next press: three maroon lines appear under D, getEntry of 1, 2 and 3, each marked sorts first; the caption says every access pays for a sort and the list is not in order between accesses. Last, the four options, with D struck through and A, B and C not struck.

A writes SortedList from scratch with its own chain. Its add(newEntry) uses getNodeBefore to find the place, and it has no add(newPosition, newEntry).

B extends LList. SortedList inherits getEntry, isEmpty and the rest, adds add(newEntry), and overrides add(newPosition, newEntry) and replace(givenPosition, newEntry) to throw an exception.

C keeps an LList in a field named list. Its add(newEntry) calls list.add(Math.abs(getPosition(newEntry)), newEntry). That is O(n) on an array list and O(n²) on a linked list, where getPosition calls getEntry up to n times.

D stores the entries in an unsorted list and sorts the list only when an entry is accessed.

Every getEntry pays for a sort first, which costs more than putting each entry in place when it is added. Between accesses the list is not in sorted order.

Answer: A, B and C [keys from the PrairieLearn twin sortedlists_designs, where these three are correct=“true”; confirm in Runestone’s results view]. Step 1. A. SortedList is written from scratch. It has its own chain and firstNode, much of its code looks like the linked list’s, its add(newEntry) finds the place with getNodeBefore as on the last slide, and there is no add(newPosition, newEntry) or replace. Step 2. B. SortedList extends LList, so it inherits getEntry, isEmpty, contains and the rest. It adds add(newEntry), and the two positional methods, add(newPosition, newEntry) and replace(givenPosition, newEntry), are overridden to throw an exception such as UnsupportedOperationException, so client code cannot use them to break the order. The book takes this one step further in 11.2: a revised base class, LinkedChainBase, keeps the chain and offers protected addFirstNode and addAfterNode instead of public positional methods, and LinkedSortedList extends it, so there is nothing to override with a throw. Step 3. C. SortedList holds a list, private ListInterface<T> list, created as new LList<>(). add(newEntry) asks getPosition where the entry belongs, takes the absolute value because getPosition returns a negative position for an entry that is not there, and calls list.add at that position. Figure 16-9: on an array-based list getEntry is O(1), so add is O(n); on a linked list getEntry is O(n) and getPosition calls it up to n times, so add is O(n²). Composition is the least code to write, and it is valid. Step 4. D. The entries go into an unsorted list, and the list is sorted when an entry is accessed. Step 5. Every getEntry has to sort first. A sort costs more than one add that keeps the order, and between accesses the list is not sorted, so getPosition, contains and remove(anEntry) cannot rely on the order. The twin’s wrong options include the same idea, entries stored unsorted with a separate method to sort them. Step 6. A, B and C. That ends the votes; next is Part 3, the Test 2 results.
