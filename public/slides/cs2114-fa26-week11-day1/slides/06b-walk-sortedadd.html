add(2, 25) places 25 at position 2, after 3. The list now reads 3, 25, 7, 12, 20.

25 is larger than 7 but comes before it, so the list is no longer in sorted order.

SortedListInterface has no add(newPosition, newEntry), so client code cannot choose a position. The list stays 3, 7, 12, 20.

Answer: C — SortedList’s add(newEntry) is responsible for putting each entry in sorted order, so client code is neither required nor allowed to choose a position [key from the PrairieLearn twin sortedlists_add; confirm in Runestone’s results view]. Step 1. Suppose SortedList extended LList and changed nothing. It would inherit add(newPosition, newEntry) and replace(givenPosition, newEntry), the two methods the 11.2 slides say a client can use to destroy the order of a sorted list. Step 2. add(2, 25) puts 25 at position 2, right after 3. Step 3. Now 25 comes before 7, so the list is not sorted, and every method that relies on the order, getPosition, contains and add itself, no longer gives correct results. Step 4. SortedListInterface, Listing 16-1, has add(newEntry), remove(anEntry) and getPosition(anEntry), plus getEntry, contains, remove(givenPosition), clear, getLength, isEmpty and toArray from the list. It has no add(newPosition, newEntry) and no replace. So this line does not compile against a SortedList, and the chain stays sorted. Step 5. The client passes only the entry. Step 6. add creates newNode with a null next. Steps 7 to 9. getNodeBefore walks from firstNode while newEntry is greater than currentNode’s data. The code calls compareTo; with ints that is the > in the captions. It is the same traversal as last week’s sorted insert. Step 10. 10 is not greater than 12, so the loop stops and getNodeBefore returns the node holding 7. nodeAfter is 12, and newNode’s next is set to it. Step 11. 7’s next is set to newNode, and the list is still sorted. The slide shows the else branch of the course’s add. If nodeBefore were null, because the list is empty or the entry is smallest, the if branch would set newNode’s next to firstNode and firstNode to newNode. Step 12, the verdict. A: contains answers whether an entry is in the list; it adds nothing. B: no combination of SortedList methods puts an entry at a position the client chooses, and none should, because that is the behaviour that breaks the order. D: the number of lines of code is not why a method is in an interface or not. C is the answer. Next is Vote 2.
