LinkedList with lastNode: add(x) at the end

  1. void add(T x) {
  2. Node newNode = new Node(x);
  3. if (isEmpty()) {
  4. firstNode = newNode;
  5. } else {
  6. lastNode.next = newNode;
  7. }
  8. lastNode = newNode;
  9. numberOfEntries++;
  10. }

add(D) on A, B, C creates a node holding D.

isEmpty() is false, so the else runs.

lastNode.next = newNode sets C’s next to D.

lastNode = newNode, so lastNode now refers to D. firstNode is unchanged.

lastNode makes adding at the end two writes with no walk. An empty list takes the if branch, and Vote 1 asks about that case.

The LinkedList Details and Options video adds one field to the list: a reference to the last node. Without it, adding at the end is the middle case at position numberOfEntries, and getNodeAt has to walk to the last node first. With it, add at the end is last week’s enqueue. Step 1. add(D) on A, B, C creates a node holding D. Step 2. The list is not empty, so the else runs. Step 3. lastNode.next = newNode sets C’s next to D. No walk: lastNode already refers to C. Step 4. lastNode = newNode, so lastNode refers to D. firstNode did not change. Step 5. Two writes, whatever the length. The if branch is the empty list, and that is the case in the first peer-instruction question, in a slightly different arrangement of these lines. The video also mentions the cost of the extra field: every method that can change the last node now has to keep lastNode correct. That comes back in Vote 2. Next is removing.
