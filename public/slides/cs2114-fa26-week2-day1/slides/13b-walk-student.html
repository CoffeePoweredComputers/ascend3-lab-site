A: javac only sees the type. C: line 3 never ran, so nothing was printed.

Answer: B — a NullPointerException, on line 2, not line 3. Beat 1: new Student[80] makes ONE object, the array, and eighty reference slots inside it — the Student constructor is never called, not once. Ask the room how many times “new Student” appears in the program: zero. Contrast with the first vote: there, new Movie() made a real object with default fields before anything was written; here nothing was made, so there are no fields to default. Beat 2: myClass[0] is a perfectly legal expression that hands you null; the crash is the dot after it, not the subscript. Beat 3: the program counter goes dark on line 2 — execution stops there, so line 3 never runs and nothing is ever printed. Read the message aloud: since Java 14 the JVM names the exact expression that was null and the method it could not call. This is the single most useful sentence they will see all semester and most of them have never read one. That is also why A is tempting and wrong: it compiled fine, javac has no way to know the slot is empty; the type checker only sees Student. Beat 4: this matters for the projects — an array of objects is filled twice, once for the array and once for every element. Beat 5: the four answers back, one strike at a time. Deliberately not drawn: any box where a Student would be. A dashed ghost Student would picture the very object the students already wrongly believe line 1 created.
