The four questions equals() asks, in order

A cascade of four gates down the middle of the slide, with an orange pill labelled other falling through them one at a time. Gate one asks whether it is null and exits to not equal. Gate two asks whether it is the same object and exits to equal, in maroon — the one exit of the four that ends in yes, and the cheap one. Gate three asks whether it is the same type and exits to not equal. Only after all three does the pill reach the fourth gate, compare the fields, whose exit is marked only now.

The order is the content: skipping the null check or the type check is what turns a passing equals() into a crash on Web-CAT’s tests. Step 2 is the cheap exit, not a formality — say why: comparing an object to itself is common, and answering it in one line costs nothing. Step 4 is the only one that reaches the fields, and by then three things are already guaranteed. Where it is written down: PrairieLearn, Java OOP → Inheritance, equals() and toString() — the module works both methods through end to end, and toString() travels with equals() in the same place. Read it before lab, not during. You will write equals() in the challenge exercise and again in all three projects, so it is worth learning once, properly.
