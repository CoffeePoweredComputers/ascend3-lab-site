the method under test

  1. public Hokie createHokie(String name) {
  2. if (name.equals("")) {
  3. return null;
  4. }
  5. return new Hokie(name);
  6. }
  1. B a Hokie never equals a String
  2. C passes, and proves nothing

One assertion per exit. C is the dangerous one: it passes.

Answer: A — createHokie has exactly two ways out, so a covering test needs one assertion for each: assertNull for the empty name, assertNotNull for any other. Step 1 — hand it the empty string: name.equals("") is true, the left exit, line 3, return null. Step 2 — hand it "Hannah": false, the right exit, line 5, a new Hokie. Two inputs, two exits; nothing else can happen in this method, and that is what "every case" means. Step 3 — A is the only option that stands at both exits and checks each for what it actually is: null is null, the Hokie is not null. Step 4 — the debrief. B: assertEquals("Hannah", createHokie("Hannah")) compares a Hokie to a String, and a Hokie never equals a String, so B fails against correct code. C: assertNotEquals("Hannah", createHokie("Hannah")) is true — but it is true of anything that is not the String "Hannah", null included — so it passes and proves nothing, and the test runner would show it green. D: assertNull(!createHokie("Hannah")) does not compile; ! applies to a boolean, not to an object reference. Name C out loud, it is the dangerous one, because it passes. A passing test is not the same as a good test. Next: 100 % coverage.
