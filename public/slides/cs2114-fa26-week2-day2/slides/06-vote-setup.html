A peer-instruction question. On the left, a test class with a private String field, a setUp method whose body is left blank, and a test that asserts the field equals the word foo. On the right, four candidates for that blank line: a new local variable declared inside setUp, an assignment inside setUp, the same assignment but in a method spelled with a capital S, and the claim that none of them work because setUp must be called by hand.

the shape all three share

  1. class Option extends TestCase {
  2. private String myStr;
  3. @Override
  4. protected void setUp() {
  5. …
  6. }
  7. public void stringTest() {
  8. assertEquals("foo", myStr);
  9. }
  10. }

  1. String myStr = "foo";

    a new local, declared inside setUp()

  2. myStr = "foo";

    assigned inside setUp()

  3. myStr = "foo";

    assigned inside a method named SetUp()

  4. None of them.

    You have to call setUp() yourself, at the top of each test.

Answer: B — and only B. A declares a brand-new local variable that dies at the closing brace — the field is still null, so the assertion fails on null against "foo". C does not even compile: the shared shape carries @Override, and javac refuses to believe SetUp overrides anything — the capital S is the entire bug, and @Override is exactly what catches it. Without @Override it would compile, never run, and leave the field null. D is the misconception the question exists for — setUp is called for you, before every test method, which is exactly why it is the place to build fixtures. Do not walk it through before the second vote.
