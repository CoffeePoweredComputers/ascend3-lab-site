PRACTICE 4 · NULL POINTER

An array of five Employees that holds none

A walkthrough of the five-line method. On the left the code, with a program-counter bar on the running line; under it a panel that stamps the exception, and under that a dashed orange panel that appears at the end holding the loop the program was missing. On the right, the heap. Line 2 grows one object — a box labelled Employee of five — and listOfEmployees’s arrow draws to it; inside the box a column of five slots, indexed 0 to 4, every one reading null. Nothing is drawn anywhere for an Employee, because no Employee exists. On line 3 slot 0 turns blue and a line under the heap reads listOfEmployees at zero is null. Then the program stops: the counter bar goes dark, slot 0 turns maroon, line 4 is marked as never run, and the panel stamps a java.lang.NullPointerException at line 3. Last, the fix: a for loop that puts a new Employee in every slot.

the code that throws

  1. public Employee[] createEmployeeList() {
  2. Employee[] listOfEmployees = new Employee[5];
  3. listOfEmployees[0].setName("Mark");
  4. return listOfEmployees; ← never runs
  5. }

Exception in thread "main" java.lang.NullPointerException at Main.createEmployeeList(Main.java:3)

what line 2 did not do

for (int i = 0; i < listOfEmployees.length; i++) { listOfEmployees[i] = new Employee(); }

One object exists: the array. Five slots, all null.

listOfEmployees[0] hands back null — no Employee to name.

It compiled. It ran. It stops here — line 4 never happens.

Same bug as Monday’s Student[80]. An array of objects is filled twice.

Answer: line 3 — a NullPointerException. Line 2 allocates five slots, not five Employees; every slot holds null until something is assigned into it, so index 0 is null and setName has nothing to call. Step 1 — new Employee[5] makes ONE object, the array, with five reference slots inside it. Ask the room how many times “new Employee” appears in the method: zero. Step 2 — listOfEmployees[0] is a perfectly legal expression that hands back null; the crash is the dot after it, not the subscript. Slot 0 goes blue: the reference being followed. Step 3 — the program counter goes dark on line 3, so line 4 never runs and nothing is ever returned. It compiled: javac only sees the type Employee, it has no way to know the slot is empty. Step 4 — the fix is a loop that puts a new Employee in every slot before anything else touches them. This is the same question they voted on in Day 1 with Student[80], which is worth saying out loud: an array of objects has to be filled twice, once for the array and once for each element. Deliberately not drawn: any box where an Employee would be. Plant: “Three of the four practice questions were the same exception. Carry that into Project 1. Now — before next class.”
