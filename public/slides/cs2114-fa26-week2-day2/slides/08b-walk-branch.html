Covered — and wrong

On the left, the method under test: getSign returns 1 when x is greater than 0, minus 1 when x is less than 0, and 0 otherwise. On the right, the four candidate tests in a two-by-two grid, lettered A to D in orange. Each option shows its own assertions in mono and, below them, the same picture of getSign: three lanes side by side, headed x greater than 0, x less than 0, and else, and footed 1, minus 1, and 0. Option by option, the assertions appear above the lanes, each one’s input drops in at the mouth of the lane it enters, that lane fills blue from the top down, and a counter reads two of three branches for A, for B and for C, and three of three for D. Last, on D, a maroon cross covers the 0 at the foot of the else lane and the 1 that D’s third assertion expects turns maroon — the lane ran, and the expectation was wrong. A caption under the code: coverage asks did this line run; it never asks was it right; Project 1 asks for both, a normal case and a bad-input case per method.

the method under test

  1. public int getSign(int x) {
  2. if (x > 0) {
  3. return 1;
  4. } else if (x < 0) {
  5. return -1;
  6. } else {
  7. return 0;
  8. }
  9. }

Coverage asks “did this line run”. It never asks “was it right”. Project 1 asks for both: a normal case and a bad-input case per method.

Answer: D — 7, minus 2 and 0 are the only set that enters all three branches. The method stays on the left the whole time, and each option keeps its own assertions above its lanes, so the room can check the claim rather than take it. Step 1 — A: 5 takes the positive lane, minus 3 the negative one; the else lane never runs. Two of three. Step 2 — B: three assertions, and the room reads that as three cases — but 10 and 2 are both positive, so they land in the same lane and the negative branch never runs. Two of three. Counting assertions is not counting branches. Step 3 — C: minus 9 and 0; the positive lane never runs. Two of three. Step 4 — D: 7, minus 2, 0 — every lane fills, three of three, 100% branch coverage. Step 5 — the sting, worth the whole question: read D’s third assertion off the slide, assertEquals(1, getSign(0)) — it expects 1 where the method returns 0, so the test fails, and the counter does not move. It still has 100% coverage. Coverage asks “did this line run”, not “is it right”, which is exactly why Project 1’s final build needs two kinds of JUnit test per method — a normal case and a bad-input case. A line that ran is not a line that was right. Plant: Part 3 — code where every line runs and one still explodes.
