This is the **codebook / coding-reliability** path. The goal: a shared, well-defined
codebook that *different people* can apply consistently <Cite id="hsieh-shannon-2005" />
<Cite id="gale-2013" />.

## Step 1 — Consolidate redundant codes

A generous first pass across the *full* set of interviews produces overlapping codes — more
than the few excerpts you saw earlier. Group ones that mean the same thing and give the
group a single clear name. Click through the logic:

## Step 2 — Write the codebook

Each consolidated code gets a **definition**, an **anchor example**, and explicit
**apply / don't-apply** rules. This is what makes a code transferable to another coder
<Cite id="krippendorff-2018" />.

<Codebook entries={codebookEntries} />

## Step 3 — Code independently, then reconcile

The team-coding loop is iterative <Cite id="saldana-2021" />:

<Steps>
1. **Code independently.** Two+ coders apply the codebook to the same transcripts, alone.
2. **Compare.** Find where you agree and where you don't.
3. **Negotiate.** Discuss disagreements; the fix is usually a sharper *definition*, not a winner.
4. **Revise the codebook** and log the decision in your audit trail.
5. **Re-code** with the revised codebook; repeat on new transcripts until stable.
</Steps>

<Callout type="warning" title="Disagreement is information, not failure">
A disagreement usually means the codebook is ambiguous. Resolving it by refining the
definition improves every future coding decision. Averaging codes or deferring to the
senior coder just hides the problem <Cite id="oconnor-joffe-2020" />.
</Callout>
